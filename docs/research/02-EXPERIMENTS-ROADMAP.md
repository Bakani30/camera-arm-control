# แผนงานและระเบียบการทดลองฉบับออกแบบ
รุ่น 1.0 · 2026-09-06 · อ่านร่วมกับ 01-RESEARCH-MASTER.md

## 1. สถานะและข้อจำกัดของแผน
เป็น roadmap วิจัย ไม่ใช่ implementation plan ที่ล็อกเทคโนโลยีแล้ว ไม่มีผลนำร่องและไม่มีตัวเลขรับประกัน ระยะ 6 เดือนเป็นเป้าหมายส่งงานหลัก เดือน 7–8 เป็นเวลาสำรองและงานเพิ่มเติม ไม่วางแผนโดยสมมติว่าทุกชั่วโมงทำงานได้เต็มประสิทธิภาพ

## 2. ลำดับงานและจุดผ่าน
### M1 — ระบบพื้นฐานปลายทางครบ (เดือน 1)
- [ ] เลือกและติดตั้งซิมหนึ่งตัวบนเครื่อง Windows แล็บ เปิดโมเดลพร้อมข้อจำกัดจริง
- [ ] รับกล้อง RGB และแสดงผลมือ ระบุเฟรม ความลึกที่ประมาณ และสถานะ tracking
- [ ] สั่งหุ่นยนต์จากท่ามือด้วยวิธีปกติ เริ่มตำแหน่งและก้ามหนีบก่อนการหมุน
- [ ] ทำ start/pause/recenter และทดสอบภาพหายโดยไม่เกิดเป้าหมายกระโดด
- [ ] บันทึก input, target, state และเวลา แล้ว replay ได้
หลักฐานผ่าน: เดโมควบคุมหนึ่งรุ่นที่ทำซ้ำได้ บันทึกครบ และทีมอธิบาย coordinate frames/คำสั่งได้ หากไม่ผ่านยังไม่เริ่มมือหลายนิ้วหรือการฝึก AI

### M2 — การใช้ส่วนร่วมและเลือก AI (เดือน 2)
- [ ] เพิ่มอีกโครงสร้าง บันทึกการเปลี่ยน profile/adapter และสิ่งที่ต้องแก้แกนกลาง
- [ ] วัด baseline กับตัวกรองบนข้อมูลเดียวกัน ระบุจุดผิดพลาดจริง
- [ ] จัดทำ AI design note ระบุ input/output/loss/ข้อมูลฝึก/การแยกข้อมูล/งบเวลา inference/ข้อจำกัด
- [ ] ทดลองขนาดเล็กหนึ่งวิธี เทียบ baseline แล้วประชุมเลือกแนวทางกับอาจารย์
หลักฐานผ่าน: การตัดสินใจ AI มีเหตุผลจากข้อมูล ไม่เลือกเพราะต้องมีคำว่า AI; หากไม่เห็นประโยชน์ให้ปรับสมมติฐานหรือรายงานขอบเขตผล ไม่ซ่อนผลลบ

### M3 — ระบบงานหลัก (เดือน 3–4)
- [ ] เพิ่มชุดมือหลายนิ้ว ตรวจ attachment, collision, actuator และท่าเริ่มในซิม
- [ ] ทำฉากหยิบ–วางและปุ่มที่มีสถานะกดจริง ใช้รูปทรงง่าย
- [ ] ประกอบและปรับเทียบแขนจริงตามคู่มือโดยตรวจ BOM ก่อนซื้อ
- [ ] เชื่อมฮาร์ดแวร์หลังซิมผ่าน ใช้พื้นที่จำกัดและวัตถุเบา
- [ ] ล็อกแบบทดลองหลัง pilot พร้อมค่าพารามิเตอร์และเกณฑ์ผ่านก่อนเก็บผลหลัก

### M4 — ผลทดลองและส่งงาน (เดือน 5–6)
- [ ] เก็บผลซ้ำทุกเงื่อนไขที่กำหนด รวมความล้มเหลว
- [ ] วิเคราะห์ผลแยกโมเดล งาน และวิธี ระบุผู้ควบคุม/จำนวนรอบ
- [ ] ตรวจ replay และการคำนวณตัวชี้วัดจากไฟล์ดิบ
- [ ] ให้สมาชิกที่ไม่ได้พัฒนาโมดูลนั้นติดตั้งและรันตามคู่มือ
- [ ] เขียนรายงานพร้อมตารางข้อจำกัดและวิดีโอประกอบ

### M5 — เวลาสำรอง/ส่วนต่อยอด (เดือน 7–8)
ใช้แก้ความเสี่ยงงานหลักก่อน สองมือทำหลังมือเดียวผ่าน ใช้พื้นที่แยกและ hand-to-robot mapping คงที่ ตรวจการสลับซ้ายขวาเมื่อมือบังหรือหาย ไม่เพิ่มการส่งของร่วมกันในระยะนี้

## 3. การแบ่งทีมที่เสนอ
| ผู้รับผิดชอบ | งานหลัก | คู่ตรวจ |
|---|---|---|
| A | กล้อง การประมาณมือ การปรับเทียบ ข้อมูลเข้า | B ตรวจ frame/unit |
| B | ซิม retargeting/AI โปรไฟล์ ขีดจำกัด | C ตรวจ command/state |
| C | ฮาร์ดแวร์ บันทึกผล ฉาก/เครื่องมือวัด | A ตรวจข้อมูลเวลา |

ไม่ให้คนใดรับผิดชอบเพียงเอกสาร ทุกคนช่วย integrate และเก็บผล ทดลองร่วมกันรายสัปดาห์ ใช้ issue ระบุเจ้าของ งานย่อย และหลักฐานเสร็จ AI ช่วยเขียนโค้ดได้ แต่เจ้าของต้องอธิบายและตรวจพฤติกรรมจริงได้

## 4. เมทริกซ์ทดลอง
### วิธี
B0: ตัวคำนวณพื้นฐาน พร้อมข้อจำกัดที่จำเป็น
B1: B0 เพิ่มตัวกรองทั่วไปที่ปรับจากข้อมูล pilot
A1: วิธี AI ที่เลือก พร้อมข้อจำกัดเทียบเท่า

หาก AI แทน retargeting หรือเพิ่ม filter ต้องระบุว่าอะไรต่างกัน ไม่ให้เปลี่ยนโมเดลอ่านมือ ค่าความเร็ว ฉาก หรือเกณฑ์สำเร็จไปพร้อมกันจนแยกผลไม่ได้ baseline ต้องปรับอย่างสมเหตุผลด้วยงบข้อมูลใกล้เคียงกัน

### งาน
T1: ตามจุด/เส้นทาง — ทุกชุดที่รองรับ ตรวจเฉพาะองศาอิสระที่ประกาศ
T2: หยิบก้อนวางถาด — ทุกชุดที่หยิบได้ในขนาดที่กำหนด
T3: กดปุ่ม — ชุดมือหลายนิ้วเป็นหลัก อุปกรณ์อื่นทดสอบได้เมื่อกำหนดวิธีสัมผัสที่เหมาะสม ไม่บังคับเทียบทุกอุปกรณ์

เก็บทั้ง replay เพื่อ isolate algorithm และ live เพื่อวัด closed-loop use replay ไม่ใช้แทนอัตราสำเร็จของผู้ใช้สด

## 5. นิยามตัวชี้วัด
- Position error: ระยะ Euclidean ระหว่าง measured pose กับ commanded target ใน frame เดียวกัน รายงาน mean/RMSE และ percentile โดยไม่สับสนกับ error ของกล้อง
- Orientation error: มุมต่างของ rotation เฉพาะแกน/งานที่รองรับ ไม่ใช้ Euler subtraction ตรง ๆ ที่มี wrap-around
- Success: ยกและปล่อยวัตถุในถาดแล้วนิ่งตามเวลาที่กำหนด หรือปุ่มผ่าน threshold การกดทางฟิสิกส์ ไม่ใช้เพียงภาพซ้อนกัน
- Completion time: เริ่มเมื่อสัญญาณเริ่มงานถึง success/timeout รายงาน timeout แยก อย่าคำนวณเฉลี่ยเฉพาะรอบสำเร็จโดยไม่บอก
- Smoothness: ความเปลี่ยนแปลงความเร็ว/ความเร่ง/jerk หรือเหตุการณ์ jump คำนวณด้วย sample times จริง ใช้การประมวลผลเดียวกันทุกวิธี และรายงาน tracking error คู่กันเพื่อไม่ให้การอยู่นิ่งได้คะแนนดีผิดความหมาย
- Latency: แยก capture/perception/retargeting/command/state และรายงาน median/p95 หากไม่มี camera hardware timestamp ให้เรียกว่า receive-to-command latency ไม่อ้าง end-to-end ทั้งหมด ต้องมีการวัดภายนอกหรือวิธีซิงก์ที่อธิบายได้สำหรับ motion-to-motion
- Tracking loss: จำนวนเหตุการณ์ ระยะเวลา และการกลับเข้าสู่การควบคุม
- Extensibility: จำนวนไฟล์/พารามิเตอร์/ส่วนแกนกลางที่เปลี่ยนและขั้นตอนที่คนทำ เวลาเป็นข้อมูลประกอบเพราะผู้พัฒนามี learning effect

รายงาน error ขณะ tracking ปกติและช่วงสูญหายแยกกัน พร้อมแสดงอัตราสูญหาย ไม่ตัดข้อมูลเสียแล้วรายงานเหมือนระบบไม่เคยพลาด

## 6. ข้อมูลฝึกและการป้องกันการรั่วไหล
- แยก train/validation/test ตาม session/ผู้ใช้/trajectory ก่อนสร้างหน้าต่างเวลา ไม่สุ่มเฟรมติดกันข้ามชุด
- บันทึก camera settings, lighting, hand side, calibration, profile, simulator timestep, controller settings, software commit, model checkpoint และ seed
- ถ้า label มาจาก optimizer ให้ระบุว่าเป็น pseudo-label ไม่ใช่ ground truth ของมือจริงหรือท่าจับที่ดีที่สุด
- causal temporal model ใช้ข้อมูลอดีตและปัจจุบันเท่านั้น วิธีใช้อนาคตต้องระบุ look-ahead latency และไม่เรียก real-time แบบไร้ delay
- กัน test set หลัง pilot ไม่ปรับ threshold จากผล test หลัก
- แยก known-robot test กับ held-out-robot test โมเดลใหม่ที่ทีมไม่ได้ใส่ profile มาก่อนไม่ได้แปลว่า pretrained AI ไม่เคยเห็นโครงสร้างนั้น
- ภาพวิดีโอผู้ร่วมทดลองเก็บด้วยความยินยอมตามขั้นตอนสถาบัน ใช้รหัสแทนชื่อในข้อมูลวิเคราะห์

## 7. แบบทดลองนำร่องที่เสนอ
ใช้สมาชิกทีมทดสอบขั้นวิศวกรรมก่อน ยังไม่อ้าง usability กับประชากรทั่วไป เสนอเริ่ม 5 รอบต่อวิธี/งานเพื่อหาความผิดพลาดและประเมินเวลาทดลอง ตัวเลขนี้เป็น pilot ไม่ใช่ sample size งานหลัก

ก่อนเก็บผลหลัก อาจารย์และทีมต้องลงทะเบียนภายใน: จำนวนผู้ควบคุม จำนวนรอบ timeout, success dwell, ขนาด/ตำแหน่งวัตถุ, allowable error, speed limits, software versions และการจัดลำดับวิธี ใช้การสลับลำดับวิธีเพื่อลดผลฝึก/ความล้า หากทดสอบเฉพาะทีมสามคนให้รายงานว่าเป็น engineering evaluation

## 8. ความเสี่ยงและการตอบสนอง
| ความเสี่ยง | หลักฐานที่ตรวจ | การตอบสนอง |
|---|---|---|
| RGB ความลึกคลาดเคลื่อน | error ตามระยะและการหมุน | ปรับเทียบและใช้ relative mapping; ไม่รับรอง absolute hand accuracy |
| โมเดลมือพร้อมใช้แต่จับไม่อยู่ | contact log/object slip | ตรวจฟิสิกส์และ baseline grasp ก่อนสรุปว่า AI ผิด |
| AI ลื่นแต่ตามช้า | error+latency+success | ลด temporal delay/ขนาดโมเดล และรายงาน trade-off |
| AI ไม่ดีกว่า baseline | test ที่ควบคุมตัวแปร | ไม่เปลี่ยนเกณฑ์เพื่อบังคับชนะ ปรึกษาอาจารย์เรื่องสมมติฐาน |
| ฮาร์ดแวร์เกินงบ | BOM รวมส่ง/อะไหล่ | เลือกรุ่นก่อนซื้อ ไม่ลดอุปกรณ์จำเป็นเพื่อให้ราคาเข้า |
| Windows/library incompatibility | prototype บนเครื่องจริง | ทดสอบ toolchain ก่อนล็อก ถ้าต้อง Linux ขอให้ทีมตัดสินก่อนเปลี่ยน |
| งานหลายแขนบาน | milestone มือเดียว | เลื่อนส่วนต่อยอดก่อน ไม่เพิ่มรุ่นโดยไม่มีโจทย์วัดผล |

## 9. สิ่งที่ต้องยืนยันก่อนเขียนแผน implementation
ซิมและเวอร์ชัน โมเดลแขน/มือจำนวนจริง ตัวอ่านภาพ โครงสร้าง AI และข้อมูลฝึก representation มือ/หุ่นยนต์ conventions เวลาและเฟรม กล้อง BOM และ driver ฮาร์ดแวร์ เกณฑ์เชิงตัวเลขหลัง pilot ประเด็นเหล่านี้เป็นงานสำรวจที่มีเจ้าของและจุดตัดสิน ไม่ใช่การให้นักพัฒนาเดา
